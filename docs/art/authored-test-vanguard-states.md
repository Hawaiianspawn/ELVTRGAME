# Authored-pixel test — Vanguard states, zero generations

**Subject:** a TEST, not a production spec — can `pixelpipe.py authored` (fenced pixel-map
block → PNG, on-palette by construction, zero PixelLab credits) produce Vanguard-type
character-state variety at the **56×60** panel cell the packed PixelLab knight/archer
states use (`task-055-pack-character-states-for-unit-variety.md`), instead of spending
credits on a PixelLab group?

**Binds to:** `docs/data/art/palette.json` (`palettes.demichrome-4.ascii_legend` — the
mechanism this whole test rests on: a spec's silhouette guide *is* the sprite) ·
`docs/art/aesthetic-direction.md` (Direction A locked, global 4-value ramp) ·
`CLASSES.md` §1 Vanguard ("reads as geometry... a Bannerman's flag is a 2-value flip...
veteran promotion = helmet pixel-tier") · `docs/art/vanguard.md` (the hero this retinue
type stands beside — Steel-dominant, flat shoulder, rectangle shield, dead-vertical pole;
this test's constants are lifted directly from that contract) ·
`docs/art/soldier-roster-v1.md` (the format precedent for authored pixel-map anchors) ·
`docs/backlog/task-055-pack-character-states-for-unit-variety.md` (the two-axis model —
TYPE picks the group, STATE picks the variation within it — and the archer-04/05 failure
mode this test must not reproduce: confusion *between* types instead of variety *within*
one).

**Deliberately does not bind to** `docs/art/retinue-militia.md` — that spec's "Liberated
militia" is a *different* silhouette family on purpose (ragged, Bone-dominant, patchwork,
zero Pale, no visor ever). This test's subject is the **armoured line-soldier** register
(regular, Steel-dominant, matched gear) — the family PixelLab's own knight group rendered,
and the one the typed-unit spearman slot actually wires.

**Pipeline note.** `Scripts/art/pixelpipe.py` currently locks `output.cell` to 48 for
every `kind` except `ui`. No request JSON is authored here — this file only produces the
five pixel-map blocks the task asked for — but running these for real through
`pixelpipe.py authored` will need either a request-side exception or a small
owner-approved widening of that lock to cover this 56×60 panel format. Flagging it now so
it isn't a surprise at generation time.

## Metaprompt

| | |
|---|---|
| **State axis (allowed to vary)** | Crown silhouette only — apex height, apex width/taper, brim width, and whether the face band is open or barred by a visor. Four independent silhouette variables, one per state, so no two states are told apart by the same trick. |
| **Held constant across all 5** | The flat shoulder line (same width, same row); the torso block (same width, same Steel fill, same single Bone belt band); the mail-skirt → greave → boot column (identical, down to the single foot-split at the very bottom); the shield rectangle (same position, width, Dark outline, single Bone band — Vanguard's registered geometry); the spear (same position, dead-vertical, 2px Dark shaft, flared Steel tip — never diagonal, never a curve); eyes as Dark recesses, **never Pale** (`palette.json.shape_carriers` reserves Pale for the hero's banner and the other three classes' marks); value-dominance role (Steel-dominant body, Bone rationed to the face patch only, Dark strictly contour/outline, Pale at 0% on every state); binary alpha; one unbroken outline. |
| **How many states this axis supports before they stop being distinguishable** | **Four cleanly, a fifth only marginally.** States 01–04 each move a *different* measurable variable — 01 is the unmarked baseline, 02 changes face-coverage (solid dark visor bar vs. open bone face), 03 changes height (a tall narrow peak, apex 5 rows above 01's dome), 04 changes width (a bulb wider than 01's dome plus a proportionally wider brim). Four variables, four states, no overlap. A fifth state has nothing left to move without reusing a variable another state already owns, or adding a decoration on top of a shape that already exists — which is exactly what state 05 does, and exactly why it is the weak one (see the readability call). |
| **Where this axis is deliberately different from PixelLab's own knight-group evidence** | PixelLab's six states landed on this same axis by accident — its "taller helm" and "rounder helm" states are this spec's 03 and 04, its "face shield" state is this spec's 02. The one deliberate departure: PixelLab's sixth state was a byte-identical duplicate of its fifth (`task-055`: "Knight 06 — byte-identical to Knight 05... cannot contribute variety"). Rather than author a literal duplicate to match that failure, state 05 here tests a *different* near-miss — not a repeated generation, but a decoration-on-an-existing-shape choice (a thin crest sitting on state 01's own dome) — a more useful failure case to have on record than reproducing a copy-paste accident. |

**Disjointness, one line.** Against `vanguard.md`'s hero: none of these five carries a
Pale rectangle or a shoulder edge wider than the torso — the hero stays the only
Pale-bearing, widest silhouette on the field. Against `retinue-militia.md`'s militia:
every militia state is Bone-dominant and ragged; every state below is Steel-dominant and
regular. The two families should never be mistaken for each other.

## The five states

The blocks below are **generated**, not hand-typed. `Scripts/art/authored_states.py`
holds the metaprompt above as four numeric knobs per state and draws the grid, so row
width, an unbroken outline, binary alpha and on-ramp values are guaranteed by
construction rather than by review. This matters: `find_pixel_blocks` in `pixelpipe.py`
silently discards a block containing any character outside the legend, so a single stray
space loses a sprite with no error. Hand-authoring a 3,360-character grid could not hold
column alignment; the first attempt at this file produced rows of 56, 58 and 62
characters with a space in the middle of one. **Edit the knobs in the script, never these
blocks.**

## Readability call

Measured against the actual generated geometry (the table above), not against intent:
**01, 02 and 04 are unmistakable, 03 is clearly distinct, and 05 is the one that fails.**
01/02/04 each move a different, immediately visible variable — 02 swaps the two-notch
open-face band for one solid dark bar across the whole face width (bone drops 7%→3%,
so the tell is a value shift as well as a shape one), 04 is visibly the widest head in
the set (its brim reaches 19px against baseline's 15px). 03's peak breaks the crown
**5 rows** above where 01's brim begins and tapers from a genuine 5px-wide mass up to
the full 15px brim over 9 rows — a real, solid triangular addition nobody would miss.

**05 does not clear the bar, and the generated geometry makes this sharper than the
design intent did.** Its crest only breaks the crown **3 rows** above baseline — 2 rows
*shorter* than 03's peak — and its narrowest point is a **single dark pixel** held for
one row before widening to 3px for two more rows and then merging into the same 9px
dome as 01. At the small end of the stated 88–176px display range, one isolated dark
pixel is roughly 1.5–3 screen px: that is at or below the threshold where a viewer
reads it as a deliberate helmet feature rather than as a stray dark speck, and if it
*is* noticed, the read it produces — "something poking up off the top of the crown" —
is the same read 03 already owns, just weaker and shorter. **05 is the fifth state this
axis cannot actually support at panel scale**, and per `task-055`'s own precedent with
Archer 04/05 (packed but not wired because they didn't read as the type), the right
call here is the same shape of decision: keep the file, drop 05 from anything that
gets wired. If a fifth crown state is wanted later, it needs either a wider sustained
minimum (closer to 03's 5px floor, not 1px) or a different attachment point than "more
height on the same crown," because height-only is 03's variable and it is already
spent.

**Depends on:** neither GDD open question (#5 flipbooks-vs-3D, #6 palette scope) — this
is a silhouette/authoring-pipeline test, not a rendering-path or palette-scope one.
#6 is resolved (strict global palette) and this file assumes it throughout; #5 is
unaffected either way since these are static anchor frames, not an animation set.

**Canon proposals:** None. The pipeline note under the header (56×60 vs. the 48px
`output.cell` lock) is an implementation flag for whoever wires this, not a canon
question.
